NOT READY FOR MICROSERVICES The system is still one Node/Express application on one EC2 with one MySQL database, legacy v1 and in-process cron. Production RPS, SLA and current production schema are unknown.

Mandatory work before splitting

  1. Security blockers: stop storing CVV, finish SQL parameterization, hash legacy passwords, restrict legacy money transfers, remove DOTENV_KEY from images and remediate 9 critical / 42 high dependency findings.
  2. Reproducible schema: capture the production baseline, align models and migrations (including ProductPurchase.booking_id), and stop building API-test schemas through sequelize.sync().
  3. Access and runtime safety: explicit public-route list, owner/RBAC checks, rate limiting, safe error responses, redacted logs and a real database health check.
  4. Data ownership: assign every table an owner, remove service-index cycles and route business writes through domain services. Shared booking, payment, identity and wallet tables require explicit compatibility contracts.
  5. Consistency: add outbox/idempotency for bookings, payments and notifications; saga/reconciliation for cancellation fees and Stripe; distributed locks for cron.
  6. Operations: run compiled JS, validate environment on startup, make CI automatic and required, and collect RPS, latency, DB and live-v1 metrics before choosing extraction candidates.
Recommended sequence: security and schema first, then data boundaries and runtime readiness. Only after these gates should low-coupling workers (reports/notifications) be considered; booking and payment cores must remain in the modular monolith for now.

К МИКРОСЕРВИСАМ НЕ ГОТОВЫ По-прежнему один Node/Express на одном EC2 и одна MySQL-БД, legacy v1 и cron внутри API. Фактические RPS, SLA и production-схема неизвестны.

Обязательные работы до разбиения

  1. Безопасность: прекратить хранение CVV, завершить параметризацию SQL, хешировать legacy-пароли, ограничить legacy-переводы, убрать DOTENV_KEY из образов, устранить 9 critical и 42 high зависимостей.
  2. Воспроизводимая схема: зафиксировать production baseline, синхронизировать модели и миграции (включая ProductPurchase.booking_id), убрать sequelize.sync() из API-тестов.
  3. Доступ и эксплуатация: явный список публичных маршрутов, owner/RBAC, rate limiting, безопасные ошибки и логи, health check БД.
  4. Владение данными: назначить владельца каждой таблицы, убрать циклы service-index, направить бизнес-записи через доменные сервисы. Для общих таблиц записей, платежей, пользователей и кошелька нужны контракты совместимости.
  5. Консистентность: outbox/idempotency для записей, платежей и уведомлений; saga/reconciliation для cancellation и Stripe; распределённые блокировки cron.
  6. Эксплуатация: запуск собранного JS, проверка env при старте, автоматический обязательный CI, замеры RPS, задержек, БД и живых v1-вызовов до выбора кандидатов на вынос.
Рекомендуемая последовательность: сначала безопасность и схема, затем границы данных и эксплуатационная готовность. Только после этого рассматривать вынос слабосвязанных workers (отчёты/уведомления); ядро записей и платежей пока оставить в модульном монолите.
