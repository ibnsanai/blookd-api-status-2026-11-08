Required before splitting the service

  1. Protect people and money: stop storing card security codes, finish safe database input handling, hash old passwords, restrict legacy transfers and remove the decryption key from application packages.
  2. Make the database reproducible: capture the real production structure, align code and change files, and test against that structure rather than a structure invented from code models.
  3. Make access and failures safe: explicit public-page list, owner checks, request limits, no internal details in errors or logs, and a health check that really tests the database.
  4. Assign data ownership: every table needs one responsible domain. Booking, payment, identity and wallet data must keep working through clear compatibility contracts, not direct writes from unrelated modules.
  5. Make background work reliable: record events safely, prevent duplicate processing, add recovery steps for payment cancellation and lock jobs across servers.
  6. Measure and gate releases: run the service from prepared code, validate configuration at startup, make checks automatic and required, and measure request rate, response time and live old-version calls.
Recommended order: safety and database structure first, then ownership and reliable background work. Only after that should low-dependency jobs such as reports and notifications be moved out. Booking and payment cores should stay in one well-structured application for now.

Обязательно до разделения сервиса

  1. Защитить людей и деньги: прекратить хранение CVV, безопасно обрабатывать ввод в БД, хешировать старые пароли, ограничить старые переводы, убрать ключ расшифровки из пакета приложения.
  2. Сделать БД воспроизводимой: снять реальную структуру production, привести код и файлы изменений к ней, тестировать на ней, а не на структуре, созданной из моделей кода.
  3. Сделать доступ и ошибки безопасными: явный список публичных страниц, проверка владельца, ограничение числа запросов, никаких внутренних деталей в ошибках и логах, настоящая проверка БД.
  4. Назначить владельцев данных: у каждой таблицы должен быть один ответственный домен. Записи, платежи, пользователи и кошелёк должны работать через понятные контракты, а не через записи из разных модулей напрямую.
  5. Сделать фоновую работу надёжной: безопасный журнал событий, защита от дублей, восстановление после ошибок отмены платежа и блокировка задач между серверами.
  6. Измерить и закрепить процесс: запуск подготовленного кода, проверка настроек при старте, автоматические обязательные проверки, измерение числа запросов, времени ответа и использования старой версии.
Рекомендуемый порядок: сначала безопасность и структура БД, затем владельцы данных и надёжный фоновый процесс. Только после этого выносить слабосвязанные задачи — отчёты и уведомления. Ядро записей и платежей пока оставить в одном хорошо структурированном приложении.
